# Kubernetes Networking Architecture Kubernetes networking operates on a sophisticated multi-layered model that abstracts container communication while maintaining performance and security. The architecture adheres to several fundamental principles that distinguish it from traditional networking approaches. ## Core Networking Model ### Flat Network Assumption Kubernetes implements a **flat network model** where every Pod receives a unique cluster-wide IP address. This eliminates the need for explicit port mapping or link management between containers, as specified in the [Kubernetes Network Model](https://kubernetes.io/docs/concepts/services-networking/). The model ensures: - Pods can communicate with other Pods across nodes without NAT - Nodes can communicate with all Pods without NAT - The IP that a Pod sees itself as is the same IP that others see it as ### Container Network Interface (CNI) The CNI specification defines how network plugins integrate with Kubernetes. The kubelet invokes CNI plugins during Pod lifecycle events: ```bash # CNI plugin execution flow ADD -> Configure network namespace DEL -> Cleanup network namespace CHECK -> Verify network configuration VERSION -> Report plugin version ``` Popular CNI implementations include: - **Calico**: BGP-based with policy enforcement via iptables/eBPF - **Flannel**: Overlay networking using VXLAN/host-gw - **Cilium**: eBPF-based with advanced observability - **Weave**: Mesh networking with built-in service discovery ## Network Layers and Components ### Pod-to-Pod Communication #### Intra-Node Communication Pods on the same node communicate through the **cbr0** (Container Bridge 0) or similar bridge interface. The container runtime creates veth pairs: ``` Pod1 (eth0) <--veth--> cbr0 <--veth--> Pod2 (eth0) ``` #### Inter-Node Communication Cross-node communication depends on the CNI implementation: **Overlay Networks (VXLAN/GRE)**: ``` Pod1 -> Node1 VTEP -> Tunnel -> Node2 VTEP -> Pod2 ``` **Route-based (BGP)**: ``` Pod1 -> Node1 routing table -> Physical network -> Node2 routing table -> Pod2 ``` ### Service Networking #### ClusterIP Implementation Services provide stable endpoints for dynamic Pod sets. The **kube-proxy** component implements service load balancing through multiple modes: **iptables mode** (default): ```bash # Example iptables rules for service 10.96.0.1:80 -A KUBE-SERVICES -d 10.96.0.1/32 -p tcp --dport 80 -j KUBE-SVC-HASH -A KUBE-SVC-HASH -m statistic --mode random --probability 0.5 -j KUBE-SEP-POD1 -A KUBE-SVC-HASH -j KUBE-SEP-POD2 ``` **IPVS mode** (higher performance): Uses Linux Virtual Server for L4 load balancing with algorithms like: - Round-robin - Least connection - Destination hashing - Source hashing #### Service Discovery Kubernetes provides two primary service discovery mechanisms: 1. **DNS-based**: CoreDNS resolves service names to ClusterIPs ``` my-service.my-namespace.svc.cluster.local -> 10.96.0.1 ``` 2. **Environment variables**: Injected into Pod containers ```bash MY_SERVICE_SERVICE_HOST=10.96.0.1 MY_SERVICE_SERVICE_PORT=80 ``` ### Ingress and Load Balancing #### Ingress Controllers Ingress controllers implement L7 load balancing and SSL termination.
